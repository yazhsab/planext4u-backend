# Media version purge acceptance plan

## Current boundary

`media.assets` tombstones block normal reads and new evidence claims. `DeleteScoped` then calls `S3Adapter.Delete`, which sends `DeleteObject` without a version ID. The AWS media bucket enables versioning and retains noncurrent versions for 30 days. This operation creates a delete marker; it does not remove prior bytes. Ordinary retries can still create more markers **before** a version purge. Migration 000006 enqueues every tombstone in `media.object_purge_state`. Forward migration 000007 gives the ordinary media process an exact-scope `SECURITY DEFINER` function to lock that row, without direct table read or write privileges; normal deletion then locks the asset row across `DeleteObject` and skips the operation once a verified purge state is recorded. A cleanup-only S3 primitive fences a key, enumerates paginated exact-key versions, deletes by version ID and verifies zero listed versions; it was exercised only against a disposable versioned MinIO bucket. `DueVersionCleaner` coordinates that primitive with due-request, policy, hold, purge-state, asset, grant and reference checks, then records an immutable per-asset evidence row and `purged_at` in the same database transaction. A separate, manual `media-version-cleanup` command now calls this boundary for one explicitly selected request/asset. It is **not deployed or connected to a scheduled task**; combined disposable PostgreSQL plus MinIO verification and a restricted-login PostgreSQL check pass, while dedicated credential provisioning and remote provider proof remain acceptance gates.

New upload grants sign `If-None-Match: *`. In a versioned bucket a current delete marker counts as no current object, so an unexpired grant can write a new version after a simple delete. Media migration 000005 now records the structurally signed conditional grant and the actual SigV4 expiry with each new session. Historical rows default to `UNKNOWN` and cannot be inferred safe; a private upload already underway must be resolved against a fence before a purge can claim that no personal versions remain. Migration 000006 checks **every** session for the asset, denies a purge mark when no session remains, and serializes new session inserts with the asset tombstone. Runtime SQL cannot rewrite the grant or asset scope, and rollback refuses to discard existing grant evidence. The current media task role deliberately has no `s3:ListBucketVersions` or `s3:DeleteObjectVersion` permission.

## Required implementation sequence

1. **Locally implemented, partial:** media-owned grant provenance defaults to `UNKNOWN` for old rows. The trusted signer result is classified only when its SigV4 query binds `If-None-Match: *`, and its signed expiry is recorded separately from service expiry. Runtime scope/provenance updates and deletes are denied; a deleted asset cannot be resurrected by direct SQL. Legacy rows remain ineligible for automatic purge until their possible upload authority has expired and a separate review permits cleanup. Cross-process purge-state coordination remains in step 2.
2. **Cleanup source and manual command locally verified; deployment pending:** PostgreSQL-backed `DeleteScoped` locks purge state first, then the asset, before object-store operations. `DueVersionCleaner` first obtains the identity due-request/current country policy/legal-hold lock, then the purge-state row, then the asset row, then checks legacy references. It holds that transaction across exact-key S3 zero-version verification and the evidence mark. A queued normal delete waits on purge state and skips its unversioned `DeleteObject` after `purged_at`. The 000006 trigger rechecks the deleted asset and **every** grant before the mark. An interrupted one-asset command can be rerun with the same exact IDs; the S3 primitive recovers a verified nonpersonal fence or creates one when the key is empty. The ordinary media runtime has no direct purge-state write or cleanup function privilege.
3. The new worker accepts **only tombstoned `IDENTITY_DOCUMENT`** assets for an exact due media-owner request, subject, tenant and country. It denies an active legal hold, unelapsed retention, current evidence claim, legacy vendor/rider reference, unknown grant or signed grant inside expiry plus five minutes. Voice, social, avatar, catalog, completion proof and other media purposes remain **outside this cleanup acceptance**. No per-asset evidence row is a terminal `ERASED`/`NO_DATA` owner receipt.
4. Wait past **every** recorded upload-grant expiry plus a reviewed clock-skew margin. Place a nonpersonal current-version fence at the exact object key. The signed conditional PUT must then fail if it races or replays. Preserve the fence after any provider error.
5. **S3 primitive and disposable combined database/object-store verification implemented:** enumerate **only the exact key** through every `ListObjectVersions` page, including object versions and delete markers. Delete each version by ID without governance-bypass headers, in bounded resumable batches. Object Lock, legal hold, access denial, missing version IDs, unexpected current-version changes and incomplete pagination must fail closed. Remove the fence only after prior versions are gone; enumerate again to confirm zero versions and markers before recording a local purge result. The primitive refuses non-versioned buckets, missing completion flags, malformed cursors, null/missing version IDs and a personal current object; it can resume an interrupted deletion only after verifying its fixed nonpersonal current fence.
6. The database cleanup role is `NOLOGIN`. The manual command requires a dedicated `planext4u_media_cleanup_login` login with no other direct role memberships or elevated attributes, explicitly assumes the cleanup role on every connection, and refuses the ordinary media login. The cleanup library rechecks `session_user`, `current_user`, elevated login attributes and other direct role memberships before each attempt, so a migration administrator's `SET ROLE` or a privilege-drifted cleanup login cannot invoke its S3 deletion path. It reads a separate database URL and S3 credentials from files, requires database `sslmode=verify-full`, and permits an HTTP S3 endpoint only on loopback. The login must be provisioned with only cleanup-role membership; a separate S3 identity must receive bucket-versioning status, exact-key current-object read and conditional fence write, version listing, and version-ID deletion. These credentials are not provisioned or wired into the ordinary runtime. The database cannot independently attest S3 state: the trusted cleanup process supplies the zero-listing result to `finish_due_version_purge`, which rechecks due scope and exact key/policy and inserts immutable evidence. Confirm AWS IAM, provider-side retention and backups before any terminal owner receipt is accepted.

The command requires `MEDIA_CLEANUP_DATABASE_URL_FILE`, `MEDIA_CLEANUP_S3_ACCESS_KEY_FILE`, `MEDIA_CLEANUP_S3_SECRET_KEY_FILE`, `MEDIA_CLEANUP_S3_REGION` and `MEDIA_CLEANUP_S3_BUCKET`. `MEDIA_CLEANUP_S3_ENDPOINT` is optional for an explicitly configured object store. Invoke it only for one reviewed, due identity-document asset with `media-version-cleanup --request-id <due-request> --asset-id <asset-uuid> --execute`. The local API image now includes this separate binary, but its service entrypoint does not run it and no cleanup credentials are mounted into the media service. It has no list-all or scheduled mode, does not use the media server's runtime credentials, and does not issue a terminal account-erasure receipt. No persistent local object was purged by this source checkpoint.

## Acceptance tests

- A disposable **versioned** S3 bucket contains multiple versions and delete markers; the purge spans more than one listing page, ignores prefix-neighbor keys, and confirms zero exact-key entries.
- An old signed PUT races the fence and later replays; neither attempt leaves personal bytes after accepted cleanup. An unknown legacy grant, an unexpired grant and a changed current fence fail closed.
- Mid-page S3 failure, denied version deletion/Object Lock, process restart and repeated purge resume without a false success or lost pending work.
- Wrong tenant/country/account, active claim, legacy application reference, legal hold and a non-tombstoned asset never invoke version deletion.
- A normal `DeleteScoped` retry racing the purge cannot add a marker after the zero-version result. A completed purge remains zero after subsequent authorized retries.
- Local tests prove DB/object-store state; an AWS IAM and versioned-bucket drill is still required before remote acceptance.

Grant provenance, runtime privilege narrowing and the normal-deletion coordination half of step 2 are implemented and [verified locally](../completion/phase-2/evidence/media-object-purge-coordination-20261030.json), including 161 fresh/rollback migrations on a disposable PostgreSQL instance. Migration 000007 repairs an already-applied 000006 deployment without rewriting its checksum or mutating existing purge rows. The [exact-key S3 primitive](../completion/phase-2/evidence/media-versioned-s3-purger-focused-20261030.json) passes local unit/vet and disposable versioned MinIO checks. A combined disposable PostgreSQL/versioned MinIO case passes under an explicit verifier assertion, including a matching immutable evidence row and zero exact-key versions. The manual command and dedicated-login check are source-verified; provisioning, deployment, AWS IAM drill, backup proof, all-purpose media cleanup and owner-erasure receipts remain open. [AWS explains that an unversioned delete adds a marker](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjects.html) and that a conditional PUT may succeed when a versioned key's current version is a delete marker ([conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)).
