# Account linking, audience checks and mobile education

This continuation targets local Android, the identity/configuration owners and the canonical admin. iOS remains deferred. Configured Firebase/Google/phone journeys and the full Phase 2 exit gate remain separate acceptance work.

## Credential linking

All three normal app runtimes expose **Profile → Sign-in methods** when Firebase is configured. Verify an existing email/password, Google or phone method, then add email/password, Google or phone to that same provider user. Phone verification supports SMS and instant Android verification. Neither callback signs in or links automatically: a challenge or verified credential is account-bound, expires after two minutes and is consumed by an explicit Verify/Add action. Late/cancelled callbacks are discarded. Firebase owns credential uniqueness; an already-used credential produces a recoverable error and never triggers an account-merge fallback. Removing methods is not offered.

The existing platform identity/provider binding is immutable. `POST /v1/me/sign-in-methods/binding` checks the live platform session and verifies the provider token, revocation/authentication tenant and current Admin SDK user record. It permits an older authentication time only to identify the correct account before reauthentication. `POST /v1/me/sign-in-methods/verify` additionally requires provider authentication within five minutes, with at most 30 seconds future skew. Both accept only `provider_token`; caller-supplied provider UID, methods, contacts or roles are rejected.

The repository locks the account then session, checks tenant/country/identity/UID/provider/active session again after the network call, synchronizes only provider-verified email/phone and appends `SIGN_IN_METHODS_VERIFIED` evidence in one transaction. An unverified replacement clears the previous verified email. Audit failure rolls back contacts. No role or platform session is granted by this endpoint. Identity migration 000005 removes runtime UPDATE/DELETE/TRUNCATE access to security events; privileged database recovery remains under deployment governance.

Mobile linking verifies the server binding before SDK reauthentication, and fresh proof before and after linking. Local grants expire after four minutes. Session/provider changes, disposal and stale responses prevent further operations. A failed response after a provider mutation is reported as an unconfirmed change; refresh reads current methods without unlocking another mutation. Password/code fields are cleared after use. Email verification is an explicit follow-up; an unverified email is not displayed as a verified platform contact. The shared provider adapter uses existing-user link/reauthentication methods, with no sign-in or user-creation fallback.

## Published introductions

The native signed-out splash and introduction remain available before provider configuration and offline. After authentication, customer/vendor/rider runtimes fetch a role/language-specific introduction through the existing CMS owner API. The admin's **CMS page builder → Create mobile introduction** creates a revision-zero draft; publication still requires the existing independent approval flow. Saving a draft does not publish it.

Reserved page IDs use `mobile-onboarding-{customer|vendor|rider}-{locale}` and routes `/app/onboarding/{role}/{locale}`. Audience is exactly the corresponding role. Supported locales are en, ta, hi, te, kn, ml, mr, bn and gu. Each page has one to eight `ONBOARDING` blocks, ordered through the page editor. Every block contains exactly `version` (1–32 ASCII letters/digits/dot/underscore/hyphen), `title` (1–120 characters) and `message` (1–1000 characters). All blocks share the edition; enabled pages require at least one enabled block. Text is rendered as native text, not HTML or executable content.

Missing translations fall back to published English. If neither exists, the app continues with its existing native introduction. Unavailable/malformed content offers retry or the standard introduction. The introduction loads at authentication/language boundaries; this does not establish live push of education into an already-open screen. The configuration owner's separate process cache defaults to 60 seconds, so accepted publication is observed within that existing cache budget. Completion is encrypted locally and keyed by content, edition, role/language and an unambiguous tenant/country/account tuple; changing fetched content repeats education even if an editor reuses the edition. Education does not grant consent or request device permissions.

Direct page and bootstrap HTTP reads filter audiences using the gateway's current trusted role header. Missing/guest/unknown roles see PUBLIC pages only; query/body audience fields never grant access. Out-of-audience direct reads return 404. Responses use no-store so a browser cache cannot carry a role selection across logout. Owning-service network isolation remains required; clients must not access internal trusted-header listeners directly. Broader delegated territory commands and master/audience definition administration remain open.

Both host and container gateway profiles must map `/v1/pages` to the configuration owner, alongside `/v1/bootstrap`. The local definitions and existing private host profile include that route. Native acceptance requires the education controller to finish without failure after login and relogin; checking only the presence of an authenticated app/controller is insufficient.

## Privacy concurrency

Consent writes are serialized in user-intent order. A pending withdrawal stops local consent use immediately; a failed write stays unconfirmed and locally denied. Earlier loads/positive write responses cannot overwrite a newer intent. Disposed controllers discard queued operations and late export/deletion results. This is not proof of durable cross-restart withdrawal delivery or cross-service erasure: real provider/device contact matching, portable cross-owner export, retention/legal holds and deletion execution still require acceptance or implementation.

Deletion-request creation and cancellation now lock and recheck the current account, tenant, country and unrevoked source session in the same PostgreSQL transaction as the lifecycle write. The security event records that session. An actual queued cancellation cannot commit after the session revocation that it waited behind; a revoked session also cannot create or cancel a request through a direct repository call. This hardens request authority, but the scheduled request still needs cross-owner erasure, retention/legal-hold decisions and terminal completion processing.
