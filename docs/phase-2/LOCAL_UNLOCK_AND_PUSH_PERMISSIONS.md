# Local unlock and notification authorization

The shared local app lock is optional and scoped to the current tenant, country and identity on this installation. Its encrypted setting uses a dedicated secure-storage namespace; session, cache, consent and payment storage are unchanged. A restored session with an enabled lock starts with all Navigator routes offstage, excluded from focus and semantics. Backgrounding relocks. Android device biometrics or screen-lock credentials confirm local access; no backend token is issued, refreshed or upgraded by that result.

Normal authenticated runtimes create the controller and expose its setting through Privacy. Fresh interactive recovery is derived only from a newly accepted provider exchange and the server session authentication time, with a five-minute age/30-second future bound. Restore and refresh cannot invent it. A successful initial read consumes that convenience. A broken local setting can be reset only after a new fresh sign-in, within a short local recovery window; backgrounding consumes the recovery opportunity. Sign-out/sign-in fallback preserves the prior saved choice until that proof exists.

An unavailable/cancelled OS challenge keeps content locked. Stale callbacks after account disposal cannot unlock or persist a new choice. Native screen privacy uses independent owner tokens: a late release cannot remove another controller's active protection. It preserves an already-secure window. Unconfirmed setting writes force a current read. Android FragmentActivity, AppCompat themes and USE_BIOMETRIC are configured for all roles. iOS remains deferred; the runtime unlock adapter currently targets Android.

Push startup now reads existing Firebase notification authorization rather than requesting it. Permission prompts belong to the explicit Android permission screen. All three normal runtimes recheck on resume. A settings return queued behind a pending registration triggers a fresh check; denied/unreadable access pauses callbacks and removes the device after in-flight writes. Removal failure stays retryable. A newer token stream result wins over an older delayed SDK read. Closed registrations cannot be restarted by logout/resume callbacks. Device permission, server channel preferences and marketing consent remain independent.

The current baseline passes 454 full workspace tests, nine archived normal debug APKs and eight actual native Android device-PIN/screen-privacy/background/storage checks. All-role normal native consolidation is running. A subsequent initial-setup cancellation issue has been reproduced: an OS exception before any storage write should preserve the confirmed disabled setting. The prepared fix passes isolated red/green checks but is not yet applied to the inventoried product source. See the Phase 2 register. The native drill uses only the dedicated synthetic AVD and removes its temporary credential. This does not prove physical fingerprint/face hardware, configured providers, release signing or production readiness.

Implementation follows the Flutter-maintained [local_auth](https://pub.dev/packages/local_auth) and [Android setup](https://pub.dev/packages/local_auth_android) documentation. Device authentication remains a local UI control over an existing authenticated session. Backend authorization and fresh authentication for sensitive commands remain authoritative.
