# Contact matching and retention

Contact matching is optional and is unavailable until an identity deployment uses the real Firebase verifier, a private contact HMAC key and a published `CONTACT_MATCHING` consent policy. The canonical admin workspace can draft this policy. Publication still uses independent approval. The policy is always optional, unique and versioned; publishing a new version requires fresh customer consent and a new sync.

On Android, the customer chooses Allow contact matching, then chooses Sync contacts. The sync action requests Android `READ_CONTACTS` and reads only normalized E.164 phone numbers on a bounded background worker, leaving the UI responsive. It does not read native contact names. Numbers without an unambiguous international form are skipped and counted locally. If the address book or scanned provider rows exceed the configured budget, the read fails without uploading a partial list. An interrupted read discards its result. The app requests a fresh Firebase ID token and sends the numbers once to identity; it does not persist the address book or provider token. Matches remain in the active account screen and disappear immediately when local consent is withdrawn, the account scope ends or current authority cannot be refreshed.

Identity verifies the current provider UID and phone credential, the signed-in platform account, country, session and current published policy. It stores a tenant-scoped HMAC of the verified owner phone and uploaded numbers, plus a key ID, policy version, expiry and revision. Editable profile phone fields never establish matching authority. A match requires both accounts to be active in the same tenant and country, both current explicit consents to the same policy, and each uploaded set to include the other's live provider-verified phone. The provider directory is read again for every match page. Results contain identity ID and display name only. The page size is at most 50 and the snapshot upload at most 10,000 numbers within a bounded request body. Provider outages deny matching.

Consent withdrawal and account disablement clear hashes in the same database transaction and advance a revision tombstone. A delayed upload cannot restore a withdrawn snapshot. Match transactions share consent locks through commit, so withdrawal acknowledgment waits for already authorized reads. Expiry clears hashes in bounded audited batches and retains revision tombstones and immutable security events. Audit failure rolls the batch back. A key rotation changes the key ID; old snapshots become unusable immediately and expire under the configured retention period (15 minutes to 30 days, default 24 hours). Key material stays in a private file and must be backed up/rotated under the deployment secret procedure; it must not be put in the admin draft, mobile build or logs.

Local verification uses disposable PostgreSQL with actual migrations, restart, mutual/one-sided matching, provider phone changes, tenant/country denial, consent lock wait, replay conflicts, audit failure rollback and expiry checks. Normal Dart and widget tests cover explicit consent, Android permission, upload suppression on withdrawal and cache-free result presentation. Android compilation confirms the manifest and native plugin compile; real Firebase and device journeys remain pending until those providers and devices are available. iOS remains deferred by user instruction.
